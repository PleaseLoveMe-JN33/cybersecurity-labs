## 参考答案

### 第一步   先检查一下自己的思路

#### 1.1   进入`/home`，查看用户目录

我的思路是：

```
cd /home
ls
```

**这个操作没有错，但它只能作为辅助排查手段，不能作为主要方法**

原因有三个：

- 并不是每个 Linux 用户都有自己的 `/home/用户名` 目录
- 系统服务账户可能使用 `/var/lib` 等其他目录作为家目录
- 用户可以在创建账户时指定任意家目录，也可以创建不带家目录的账户

**真正应该检查的是**`etc/passwd`

**这个文件保存了系统本地用户账户的基本信息**

请敲下面这个命令：

```
cat /etc/passwd
```

不过，企业环境中还可能使用 LDAP、SSSD 等集中式身份认证服务

因此，更推荐使用：

```
getent passwd
```

**它可以通过系统配置的用户信息数据库查询账户，不只是读取 `/etc/passwd`**

#### 1.2   我们深究一下为什么两条指令有差别

##### 1.2.1   假设你在自己的 Kali 虚拟机中创建了一个账户：

```
useradd -m john
```

> `-m`是选项，意为创建家目录
>
> 这样就会出现一个`/home/john`
>
> 顺便认识一下几个其他的相关选项
>
> - `-M`：不创建家目录
> - `-d`：指定家目录路径
> - `-s`：指定登录Shell
> - `-u`：指定UID
> - `-g`：指定主要用户组
> - `-G`：指定附加用户组

你创建了一个叫 `john` 的用户

那么 Linux 就需要保存这个用户的信息，例如：

- 用户名是多少
- UID 是多少？
- 属于哪个用户组？
- 家目录在哪里？
- 使用什么 Shell？

这些信息通常会记录在：

```
/etc/passwd
```

你可以执行：

```
cat /etc/passwd
```

看到类似这样的内容：

```
root:x:0:0:root:/root:/bin/bash
bin:x:1:1:bin:/bin:/sbin/nologin
johnwang:x:1000:1000:CentOS7:/home/johnwang:/bin/bash
jack:x:1001:1001::/home/jack:/bin/bash
```

> 标准格式：
>
> **用户名:密码占位符:UID:GID:用户描述:家目录:登录Shell**



##### 1.2.2   假设这不是你的个人Kali，而是一家企业的Linux服务器呢？

先想象一个企业环境😁😁😁

某家公司有：

- 100 台 Linux 服务器
- 200 名员工
- 每名员工都可能需要登录其中一部分服务器
- 员工离职后，需要统一禁用其账户

假设公司采用最简单的方式：每台服务器独立创建账户

那么会发生什么？

例如，公司有一名员工叫 Alice👧

管理员需要让 Alice 使用 100 台服务器，就可能需要在每台服务器上创建 Alice 账户

> 100台服务器100个独立的账户，还是同一个人的，吃饱了撑着没事干给自己找罪受是吧，重复输同一个密码100遍我直接原地辞职了，万一哪天还来这种情况
>
> 老兄，把24-55号服务器密码改了，65-77号相关账户资料删了，那很裂开了

于是，企业可以采用另一种方式：

**集中式身份管理**

**让公司建立一个统一的账户目录，所有服务器都可以向它查询用户信息**

这样一来，管理员可以在**统一身份管理系统**中创建 Alice 的账户，然后根据**授权策略**让不同服务器识别她

员工离职时，也可以从统一身份管理系统中禁用账户，而不必逐台手工删除

这就是为什么企业会使用集中式身份认证和账户管理服务



##### 1.2.3   LDAP和SSSD到底是什么？

**LDAP：集中式目录服务的访问协议**

LDAP 全称为轻量级目录访问协议

先把它理解成一种协议，用来访问和查询目录服务中的信息

例如，企业可以建立一个 LDAP 目录服务，其中保存：

```
用户：Alice
UID：20001
GID：20001
家目录：/home/alice
Shell：/bin/bash
```

当 Linux 服务器需要查询 Alice 的账户信息时，就可以通过 LDAP 访问企业的目录服务

**这里要注意一个细节：**

**LDAP 本身是协议，不等于某个具体的数据库软件**

**Microsoft Active Directory 也支持 LDAP 协议，因此 Linux 服务器可以通过相应配置对接企业的 AD 域环境**



**SSSD ：帮助Linux对接集中式身份服务的组件**

SSSD 全称为系统安全服务守护进程

这个名字听起来复杂，其实你可以先把它理解为：

> 一个运行在 Linux 本地的身份服务中间层，帮助 Linux 获取远程账户信息，并支持缓存、身份查询以及认证相关功能

例如：

公司有一个 LDAP 目录服务，里面有 Alice 的账户信息

Linux 服务器安装并配置了 SSSD 后，就可以让 SSSD 帮助系统与 LDAP 服务进行通信

```
SSSD 在企业 Linux 环境中的位置如下图所示：

      Linux 用户或系统程序发起查询
                  ↓
   NSS 接收请求并决定去哪里查询用户信息
                  ↓
       SSSD 负责获取远程用户信息
                  ↓
LDAP / Active Directory 提供企业集中管理的账户信息
                  ↓
              返回查询结果
```

补充：

SSSD 不仅能对接 LDAP，也能对接 Active Directory、FreeIPA 等身份服务

它还可以提供身份信息缓存，减少对远程服务的重复查询



##### 1.2.4   最重要的部分：NSS究竟是什么？

为什么推荐用`getent passwd`，而不是只使用`cat /etc/passwd`

关键就在**NSS**

NSS 全称：Name Service Switch，名称服务交换机制

> 先把它理解为 Linux 的一个统一查询入口
>
> Linux 在需要获取用户信息时，不一定只查看 `/etc/passwd`，它可以根据 NSS 的配置，决定去哪些地方查找

那么，Linux 怎么知道应该去哪里查询？

答案就在这个文件：

```
cat /etc/nsswitch.conf
```

**这是整个知识点的核心**

打开后，你看到：

```
passwd: files systemd sss
group:  files systemd sss
shadow: files systemd
```

我们重点看第一行：

```
passwd: files systemd sss
```

|  名称   |               含义               |
| :-----: | :------------------------------: |
| passwd  |         查询用户账户信息         |
|  files  | 查询本地文件，例如 `/etc/passwd` |
| systemd |   查询 systemd 提供的用户信息    |
|   sss   |      通过 SSSD 查询身份信息      |

**这里的顺序也很重要**

`files` 排在前面，`sss` 排在后面

这意味着系统会根据配置的顺序和查询结果，依次使用相应的信息来源，具体的停止条件和失败处理还可以通过 NSS 配置规则调整



##### 1.2.5   现在来看`cat`和`getent`的区别

假设某企业服务器存在以下配置：

```
/etc/passwd


root:x:0:0:root:/root:/bin/bash
john:x:1000:1000:John:/home/john:/bin/bash
```

```
/etc/nsswitch.conf


passwd: files sss
```

企业 LDAP 目录中还有一个账户：

```
alice
```

Alice 的账户信息并没有直接写进这台服务器的 `/etc/passwd`

这时候，你分别执行两个命令

**操作A：**

```
cat /etc/passwd
```

结果：

```
root:x:0:0:root:/root:/bin/bash
john:x:1000:1000:John:/home/john:/bin/bash
```

为什么没有 Alice？

因为 `cat` 只是读取 `/etc/passwd` 这个文件的内容

它不会主动联系 LDAP，也不会查询 SSSD

**操作B：**

```
getent passwd
```

在远程账户枚举正常启用且目录服务可用的情况下，结果可能包含：

```
root:x:0:0:root:/root:/bin/bash
john:x:1000:1000:John:/home/john:/bin/bash
alice:*:20001:20001:Alice:/home/alice:/bin/bash
```

为什么出现 Alice 了？

因为 `getent` 使用 NSS 机制查询配置好的用户信息来源

它不仅查询本地的 `/etc/passwd`，还可以通过 SSSD 获取远程身份信息

**不过，这里有一个非常重要的进阶细节：**

`getent passwd` 并不保证一定能列出 LDAP 或 AD 中的全部用户

例如，SSSD 可以配置为不进行远程账户的批量枚举，但仍然允许查询指定用户

所以，在企业服务器上，还可以使用：

```
getent passwd alice
```

**这个命令尤其适合在无法完整枚举远程账户的环境中检查具体用户**



##### 1.2.6   回到你的企业安全运维任务，应该怎么做？

现在你已经理解这些概念了

假设你接到一台企业 Linux 服务器，需要排查是否存在未经授权的账户

你该怎么做？

###### 第一步：检查NSS配置

```
cat /etc/nsswitch.conf
```

找到：

```
passwd:
```

看看系统配置了哪些用户信息来源

###### 第二步：检查本地用户

```
cat /etc/passwd
```

了解本地账户有哪些

###### 第三步：检查NSS账户查询结果

```
getent passwd
```

看看系统通过配置的账户信息来源能够查询到哪些用户

###### 第四步：对比检查

假设：

```
getent passwd alice
```

能够查到Alice，但：

```
grep '^alice:' /etc/passwd
```

> 这条命令的作用是：
>
> 在`/etc/passwd`文件中查找用户名为alice的本地用户账户
>
> grep：在文本中搜索匹配指定模式的内容

什么也没有

这说明 Alice 可能来自 SSSD、其他远程身份服务，或者其他 NSS 数据源，而不是本地 `/etc/passwd`

**这并不代表 Alice 是异常账户**

**你需要进一步确认：**

- Alice 是不是公司的正式员工？
- 她是否被授权登录这台服务器？
- 她的账户是否属于企业统一身份管理系统？
- 她是否具有不应该拥有的 sudo 权限？

##### 1.2.7   安排一个小实验

在Kali虚拟机里执行以下命令

- 查看本地账户文件

```
cat /etc/passwd
```

- 查看NSS配置

```
grep '^passwd:' /etc/nsswitch.conf
```

- 使用getent查询账户

```
getent passwd
```

- 查询指定账户

```
getent passwd root
```

- 对比本地与NSS结果

```
grep '^root:' /etc/passwd && getent passwd root
```

## 实验操作3：创建用户并检查账户信息

**模拟工作场景：**

公司新招聘了一名安全运维人员，需要为他创建一个 Linux 普通用户，并核实账户配置

首先确认当前身份：

```
whoami
```

确认自己处于 root 身份

创建一个实验用户：

```
useradd -m lab_analyst
```

设置密码：

```
passwd lab_analyst
```

接着执行：

```
id lab_analyst						检查UID、GID 和所属组

getent passwd lab_analyst			检查账户数据库中的用户信息

ls -ld /home/lab_analyst			检查家目录是否存在及其属性
```

**验收标准：** 你能够解释一条用户账户记录中的每个字段，并确认新建用户的 UID、GID、家目录和登录 Shell
